# 数据组织规范（媒体库 + 索引 + 同步）

> 原则：**自用优先，不迁就任何第三方软件**。元数据是磁盘上的 JSON，索引是可重建的 SQLite，两者都能 diff、能手工改、能进 git。
> 顺带能兼容 Jellyfin 就兼容，不能就算了——不为它改变结构。

---

│        └─ …
│     └─ 2021\
│        └─ 2021-12-17 民族脊梁：鲁迅\      ← 一稿多段
│           ├─ meta.json                    ← 22 段的总条目
│           ├─ transcript.md
│           ├─ blocks.json

**为什么一节目一文件夹**：增量同步按文件夹打包最自然；人能直接翻；单期出问题只影响一个目录。

**为什么 meta.json 是唯一真源**：`library.db`、`manifest.json`、手机端的索引，全部都从 meta.json 派生。改错了删库重建即可。

### 2.0 `flags`：无文稿节目的容错位

全库有约 **69 段音频没有对应文稿**（0.2%），另有 63 篇文稿没有音频。这两类都必须**入库但不阻塞**：

| 字段 | 含义 | 下游行为 |
|---|---|---|
| `has_transcript` | 有没有正文 | false 时：不出 `blocks.json`，阅读页显示「暂无文字版」 |
| `text_source` | `doc` / `asr` / `none` | ASR 补齐后回填为 `asr`，管线重跑只更新文本相关字段 |
| `needs_asr` | 待补 | 汇总成 `needs_asr.json`，交给 GPU 批量转写 |
| `has_compilation` | 含超长合集段 | 播放器可折叠，不出现在随机队列 |

**硬性要求：任何环节都不能假设 `blocks.json` 存在。** 检索、播放、同步、推荐都要有对应的空分支。

### 2.1 维度设计（为什么是这几个）

你说的"风格 / 类型 / 难度 / 关键词"是对的，但拆得比你说的更细，因为有几个容易混：

| 维度 | 取值 | 为什么单独存在 |
|---|---|---|
| `domain` | 天文·物理·化学·生物·医学·地球·数学·计算机·工程·历史·人文社科·军事·哲学·杂项 | 一级学科，硬过滤用 |
| `topics` | 自由词，2–6 个 | 二级主题，"火星""黑洞"这类，检索主力 |
| `content_type` | 科普讲解·人物传记·历史叙事·时事评论·答疑互动·实验演示·系列专题·杂谈漫聊 | 你说的"类型"，决定用户预期 |
| `style` | 轻松幽默·严肃硬核·故事化·对话访谈·激情演讲·冷静克制·怀旧抒情 | 你说的"风格"，1–2 个 |
| `level` | 1 入门 · 2 进阶 · 3 硬核 | **知识门槛** |
| `cognitive_load` | 1–5 | **听的时候要不要动脑**——和 level 不是一回事：讲黑洞可以很硬核但不费脑（纯听个震撼），讲博弈论可以很入门但费脑 |
| `pace` | 慢·中·快 | 睡前最关键的单一指标 |
| `emotional_tone` | 好奇·平静·震撼·沉痛·热血·怀旧·轻松·紧张 | "想听点轻松的"直接命中这里 |
| `has_story` | bool | "想听个故事" vs "想听人讲道理" |
| `needs_prior` | bool | 系列第 3 幕依赖前情 |
| `scene` | 睡前·通勤·运动·做饭·专注 | 场景是复合标签，便于一键 |

**`sleep_friendly` 和 `energy` 不参与打标，由规则推导**：

```
sleep_friendly = level <= 2
              && cognitive_load <= 3
              && pace in [慢, 中]
              && !has_loud_sfx
              && duration <= 2400
```

推导比让 LLM 猜更稳，而且改规则就全库重算，不用重新花钱打标。

### 2.2 打标的硬约束

维度一多，LLM 最容易犯的错是**每个字段都想填满、还爱造词**。所以：

- 每个枚举维度给**固定词表**，只能选，不能造
- 每维度最多 2 个值（`domain` 最多 3）
- `topics` 和 `keywords` 允许自由，但去重、长度 ≤ 8 字
- 输出用 JSON Schema 强约束（`enum` + `maxItems`）
- **打标跑两轮**：第一轮生成，第二轮只做自检（"这几个标签真的对吗，删掉不准确的"）。成本翻倍，也就 ¥40
- 结果落盘 `cache\tagging\<id>.json`，重跑不重复花钱

## 3. `blocks.json` — 正文结构与时间锚点

```json
{
  "article_id": "2049-2016-0502",
  "chars": 1844,
  "anchor_source": "ratio+silence",     // 或 "asr-align"
  "blocks": [
    { "i": 0, "type": "p",   "text": "生活不止眼前的苟且……", "start_ms": 0,     "end_ms": 14200 },
    { "i": 1, "type": "p",   "text": "我今天就给大家介绍三个……", "start_ms": 14200, "end_ms": 33800 },
    { "i": 2, "type": "img", "src": "images/01.jpg", "caption": "薛定谔", "start_ms": 33800 },
    { "i": 3, "type": "h2",  "text": "三、海森堡把妹法", "start_ms": 52100 }
  ]
}
```

- 无 GPU：`196 字/分` + `silencedetect` 补偿，误差 ±20 秒
- 有 GPU：替换成 ASR 实测值，`anchor_source` 改 `asr-align`，误差 ±0.5 秒

## 4. 段落级索引

### 4.1 分块规则

- 以自然段为最小单位（实测中位 19 段/篇，平均每段约 130 字）
- 小于 80 字的相邻段合并；大于 400 字的按句号切
- 每块保留 `start_ms`（来自 blocks）和 `char_start`
- 实测全库约 **5 万块**

### 4.2 存储

```sql
-- 文章级（约 3,038 行）
CREATE TABLE article (
  id TEXT PRIMARY KEY, title TEXT, date TEXT, year INT, seq INT,
  duration_sec INT, series_id TEXT, part_no INT, standalone INT,
  summary TEXT, vec BLOB              -- 512×fp16 = 1KB
);

-- 段落级（约 50,000 行）
CREATE TABLE chunk (
  article_id TEXT, idx INT, text TEXT,
  char_start INT, start_ms INT, end_ms INT,
  vec BLOB,                          -- 512×fp16 = 1KB
  PRIMARY KEY (article_id, idx)
);

-- 多维标签（约 12 万行）
CREATE TABLE tag (
  article_id TEXT, dim TEXT, value TEXT, weight REAL
);

-- 文章级 bigram 倒排（约 300 万行，覆盖 3,038 篇）
CREATE TABLE bigram (
  term TEXT, article_id TEXT, tf INT, PRIMARY KEY (term, article_id)
);
```

体积估算：chunk 的 vec 50MB + text 30MB + bigram 60MB + 其他 ≈ **180MB**。手机 200GB 完全无所谓。

### 4.3 关键决策：段落级**不做**倒排

5 万块建倒排要 300 万行，检索时还要合并，收益不大。替代方案：

```
第一步：文章级 bigram + 文章级向量 → 候选 40 篇（<10ms）
第二步：在这 40 篇的 ~700 个 chunk 里线性扫描（字符串 + 向量）→ 命中段（<5ms）
```

700 个 chunk 在内存里扫一遍，比查任何索引都快，而且实现只有几十行。

## 5. `manifest.json` — 增量同步协议

```json
{
  "library_version": "2026.11.22-1",
  "schema_version": 2,
  "counts": { "articles": 3038, "parts": 3281 },
  "index": { "path": "library.db", "size": 188000000, "sha1": "…" },
  "items": [
    {
      "id": "2049-2016-0502",
      "v": 3,
      "bytes": 5210000,
      "files": [
        { "p": "shows/2049/2016/2016-05-02 数学三大危机/audio.m4a", "s": 4800000, "h": "…" },
        { "p": "…/meta.json", "s": 3200, "h": "…" },
        { "p": "…/blocks.json", "s": 18000, "h": "…" }
      ]
    }
  ]
}
```

同步流程：

```
App: GET /manifest.json
  → 与本地 manifest 比对 id + v + h
  → 拉新增/变更（按 item 粒度，不是一个巨大 zip）
  → 校验 sha1 → 写入 → 更新本地 manifest
```

要点：
- **按 item 粒度增量**，不是整包替换。一次只加 15–20 期，几 MB 到几百 MB
- `v` 是内容版本号，任何文件变了就 +1
- 索引库 `library.db` 单独传（150MB，可 gzip 到 40MB）；也可以让 App 从 meta.json 本地重建（更慢但更省流量）
- 支持断点续传（HTTP Range）

## 6. `2049ctl` — PC 端刮削工具

```
2049ctl scan      # 扫描源目录，更新 sources.jsonl（新增/变更/删除）
2049ctl build     # 增量构建：解析 → 转码 → 打标 → 建索引
2049ctl doctor    # 自检：缺失文件、时长偏差、标签漂移、孤立条目
2049ctl export    # 生成 manifest + 同步包
2049ctl serve     # 起本地同步服务（HTTP，给手机拉）
2049ctl preview   # 生成静态 HTML 页面，肉眼检查库
```

常用参数：

```
--since 2026-10-01     只处理这个日期之后的新增
--only-build 索引      只重建 db，不碰媒体
--retag                强制重新打标（改词表后用）
--dry-run              只打印将要做什么，不动文件
```

`build` 的幂等规则：

| 条件 | 行为 |
|---|---|
| `source_sha1` 未变 且 `pipeline.version` 未变 | 跳过 |
| 源变了，`pipeline.version` 没变 | 只重跑受影响阶段 |
| `pipeline.version` 变了 | 全量重跑，但打标结果从 `cache\tagging\` 读（不重复花钱） |
| `meta.json` 里 `locked` 非空 | 该字段不覆盖 |

## 7. 自检（替代"Jellyfin 能扫出来"这个验收标准）

不兼容 Jellyfin 之后，得换个能真检验的手段：

**`2049ctl doctor` 检查项**

| 检查 | 阈值 |
|---|---|
| 每个 article 都有 meta.json / blocks.json / audio | 100% |
| 时长总和 | 864.5 小时 ±1% |
| 标题重复 | 0（已知 4 组白名单） |
| blocks 字数 vs meta.chars | 差异 < 2% |
| blocks 最后 end_ms vs 音频时长 | 差异 < 30 秒 |
| 标签取值全部在词表内 | 100% |
| 向量维度一致 | 100% |
| 孤立文件（有音频无 meta） | 0 |

**`2049ctl preview`** 生成一个静态 HTML：按年分页，每期显示封面 + 标题 + 标签 + 时长，点开看正文和波形。3,038 期一页翻下来，比任何报表都直观。
