## 0. 结论

架构不变：**PC 端一次性建索引 → 手机端本地召回 → DeepSeek 精排 → Media3 播放**。

但实测推翻了几处假设，需要修正设计：

1. **不是"一期 25 分钟"，是"一期 11.6 分钟"** —— 睡前 30 分钟要放 2–3 期，**无缝连播**比"选对一期"更影响体感
2. **不是"一稿一音频"，是"一稿多段"** —— 鲁迅那套是 1 篇文稿对 22 段音频，**数据模型必须是两层**
3. **语速实测 196 字/分钟** —— "匀速滚动"有了真实系数，比例映射误差比预想小
4. **产出物不该是"一个私有索引"，而是"一个标准媒体库"** —— 目录统一、元数据落盘，`library.db` 只是它的派生物，可随时重建。见 [数据组织规范](媒体库规范.md)
5. **检索是三级不是两级** —— 节目级召回 → **段落级定位** → LLM 精排。段落级让"某期某一段讲了火星"能被找出来，并直接从那一段开播
6. **不迁就任何第三方软件** —— 元数据按我们自己的检索需求设计，能顺便兼容 Jellyfin 就兼容，不能就算了

## 2. 实测带来的四个设计修正

### 2.1 一期 11.6 分钟 → 连播体验是核心

68% 的节目在 5–15 分钟。睡前 30 分钟实际要放 **2–3 期**。这意味着：

- **无缝连播**（gapless）不是锦上添花，是主路径：一期结束时不能停顿、不能没有下一期
- 队列至少要 6–10 期才够撑满一次睡眠
- **"听完这期"和"定时 30 分钟"是两种不同的结束方式**，都要有
- 自动续播时音量不能跳（响度归一化在短节目上更明显，因为切换更频繁）

### 2.2 一稿多段 → 数据模型必须两层

实测发现最长的一类节目是这样拆的：

```
民族脊梁：鲁迅.doc              ← 1 篇文稿
2021\0【民族脊梁：鲁迅】序幕.mp3     ← 22 段音频
2021\01【民族脊梁：鲁迅】第一幕：周樟寿.mp3
...
2021\21【民族脊梁：鲁迅】终章.mp3
```

**推荐的数据模型**：

```
Series（系列，可选）
 └ Article（节目 = 一篇文稿）
    └ AudioPart（音频段，1..N）
```

关键字段：

| 层 | 字段 |
|---|---|
| Article | id, title, date, series_id, doc_path, char_count, summary, tags, mood, scene, level, standalone |
| AudioPart | id, article_id, part_no, title, mp3_path, duration, **char_start / char_end** |

`char_start/char_end` 表示**这段音频对应文稿的哪一段字符区间**。多段音频共享一篇文稿时，按"该段时长 ÷ 全套总时长 × 总字数"分配，误差在 10% 以内——因为每段都有 20 分钟以上，比例法够用。

这就解决了"听第 5 幕时，文字该滚到哪"的问题，而且不需要任何对齐。

### 2.3 语速 196 字/分钟 → 滚动映射有了真实系数

之前担心的"匀速滚动漂移"其实没那么严重：

- 中位 2,506 字 / 11.6 分钟 = **3.6 字/秒**
- 用 196 字/分 建映射，再叠 `silencedetect` 的静音补偿，误差能压到 **±20 秒以内**
- 再给一个手动校准（点一下"我听到这里"），基本就锁死了

### 2.4 零时间戳已确认 → 对齐方案彻底出局

3,038 份文稿，0 份带时间戳。**不要在这个方向上再做任何投入**。章节级锚点、逐字高亮、段落跳转，全部走"时长比例推算"。

## 3. 系列识别：实测有三套并存

| 形态 | 数量 | 例子 |
|---|---|---|
| **【】专题** | 84 组 / 362 期 | 【未来预言】26 期、【暗黑无界】26 期、【生命密码】18 期 |
| **SxxExx 编号** | 263 期 | `S01E01我们回来了.mp3` … `S03E60…`（早期长篇） |
| **「之」连接** | 278 期 | 中国十大领先技术**之**量子通信 |
| **（上）（下）/ 第一幕** | 52 + ~570 段 | 鲁迅的收入（上/下）、民族脊梁 22 幕 |

你说的"1,2,3,4 后缀"大概率指**第三类**——一稿多段的拆幕。这类要靠 `char_start` 顺序串起来。

**建议的解析顺序**：`SxxExx` > `【】` > `（上/下）` > `第一幕/第N集` > `之` > 标题相似度聚类。规则能覆盖约 700 期，剩下的 2,500 期本来就是独立短篇，不需要系列。

## 5. PC 管线

### 5.1 环境（当前机器缺什么）

| 需要 | 现状 | 处理 |
|---|---|---|
| Python | ✅ 3.14.7 已装 | — |
| `oeffile` / `mutagen` | ❌ | `pip install olefile mutagen`（已验证可装） |
| **ffmpeg** | ❌ **没有** | `winget install Gyan.FFmpeg`，一条命令 |
| LibreOffice | ❌ 没有 | **不需要**——已用纯 Python 解析 Word97 |

我已经写好并跑通了一个 Word 97 解析器（`scripts/doc97.py`，OLE + piece table，处理压缩文本片），3,038/3,039 成功。

### 5.2 文稿解析

- 纯 Python，**不需要 Word / LibreOffice / antiword**
- 注意 2016 年的部分文件用「压缩 8 位文本片」存储，直接按 UTF-16 解码会全乱——必须走 piece table
- 控制字符归一：`\r`→换行、`\x07`→换行、`\x0b`→换行
- 输出：`[{type: paragraph, text}]`，标题从文件名取（正文首段是开场白，不含标题）

### 5.3 音频

- 重编码一次，把响度烤进去：`-ac 1 -c:a aac -b:a 96k -af loudnorm=I=-16:TP=-1.5:LRA=11`
- 46.66 GB → **约 25 GB**，864 小时在普通 CPU 上约 6–10 小时
- 同时跑 `silencedetect` 拿静音区间，供滚动映射用
- 异常值：有 1 段 580 分钟的，播放器上要单独处理（或标记为"合集"）

### 5.4 打标

每篇文稿约 3,000 token 输入：

```json
{ "id": "a_20211217_luxun", "title": "民族脊梁：鲁迅",
  "series": "民族脊梁", "parts": 22, "total_duration_sec": 52000,
  "summary": "以二十幕讲完鲁迅一生，从周樟寿到民族魂。",
  "tags": ["鲁迅", "中国近代史", "文学", "人物传记"],
  "mood": ["深沉", "激昂"], "scene": ["睡前", "通勤"],
  "level": "进阶", "standalone": false }
```

- **3,039 篇 × 3,000 token ≈ 910 万 token → 一次性 ¥10–20**
- `mood` / `scene` 用固定词表（20 情绪 + 12 场景）
- 长篇必须标 `standalone: false`（22 幕不能乱序听），短篇默认 `true`
- 实测只有 151 篇有"插图"文字标记，所以配图**按文件夹归属**到 Article，个别有 `鲁迅插图\01\` 这种编号子目录的可以按幕归档

## 6. 检索（3,281 期 → 必须两段式）

### 6.1 三段式

**① LLM-A 意图解析**（~1k token，0.5–1s）

```
"今天想听点轻松有趣的" → { mood:["轻松","幽默"], scene:["睡前"],
                          duration_max:1800, exclude:["硬核"], series:null }
```

**② 本地召回**（<50ms）

- bigram 倒排（"火星探测"→ 火星/星探/探测）
- 标签过滤（mood/scene/level/standalone）
- 时长过滤（睡前偏好 10–20 分钟）
- 系列配额：同一 series 最多留 2 条
- 向量可选：3,281 × 1024 × 4B = **13.4 MB**，全内存暴力算余弦，够快

**③ LLM-B 精排**（8–12k token）

```json
{ "pick": {"id":"a_2023_0412","part":1,"reason":"讲火星水，11 分钟，语速平缓"},
  "queue": [ {"id":"a_2023_0501"}, {"id":"a_2022_1103"} ],
  "confidence": 0.86 }
```

**队列组装规则**（实测时长决定的）：
1. 若选中的是长篇第 k 幕 → 优先接第 k+1 幕
2. 补 3–5 期同标签短篇
3. 总时长凑到 **35–45 分钟**（一次睡眠的量），而不是固定条数

### 6.2 全目录模式

3,281 期 × 130 token ≈ **43 万 token**。1M 上下文塞得下，但每次要传约 1 MB。**只做兜底**：本地召回分数普遍低时切一次。

### 6.3 成本

- 单次点播 ¥0.03 / 2–4 秒
- 每月 300 次 ≈ ¥9
- 打标一次性 ¥10–20

## 7. 手机端技术栈

| 层 | 选型 |
|---|---|
| 语言/UI | Kotlin + Jetpack Compose (M3) |
| **播放** | **Media3 ExoPlayer + MediaSessionService**，`setMediaItems` + 无缝连播 |
| 数据 | Room（Article / AudioPart / Series / FTS-bigram） |
| 网络 | OkHttp + SSE |
| 图片 | Coil |
| minSdk | 26 |

**必须做对的播放细节**（实测短节目放大了这些）：
- 期与期之间 **gapless**，不能有 0.5 秒空白
- 响度归一（已烤进文件）
- 睡眠定时：15/30/45/60 分钟 / 听完这期，最后 30 秒淡出
- 断点续播 + 来电后自动恢复
- 息屏时 UI 不渲染

## 12. 3 张 3090 能干什么

只有一件事真正需要 GPU：**句级时间戳**。其余都是"能跑但没必要"。

| 用途 | 值不值 | 说明 |
|---|---|---|
| **句级对齐** | 值，但先试点 | faster-whisper large-v3-turbo 出词级时间戳 + 字符级 DP 映射回 DOC 文本。864 小时音频，单卡 12–15 小时，三卡并行 4–5 小时 |
| 文稿-音频一致性校验 | 值 | ASR 文本与 DOC 的相似度低于阈值 → 说明这对不上，能揪出那 572 段"只在音频"的错配 |
| 本地 LLM 打标 | **不值** | 全库 API 打标才 ¥10–20，本地部署 Qwen3-32B 的维护成本远高于省下的钱。GPU 留给对齐 |
| 向量化 | 无所谓 | bge-m3 全库几秒，本来就便宜 |

对齐解锁的东西：
- 滚动从"±20 秒估算"变成"±0.5 秒实测"
- "跳到讲火星那段"真正可用
- 章节可以按话题切换点自动切

代价是一条 whisper 依赖链（faster-whisper + 模型权重 + CUDA 环境 + 多卡进程池），管线复杂度上一个台阶。

**建议**：先拿 20 期跑试点（1 小时 GPU），人工听 3 期看准不准。准就全量跑一晚挂在 P1.5；不准就不做——v2 的比例滚动在 11.6 分钟的短节目上已经够用。
